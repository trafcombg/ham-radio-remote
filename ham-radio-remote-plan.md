# План за разработка — Дистанционно управление на Icom радиостанции

## Контекст на проекта

**Цел:** Клиент-сървър система за отдалечено управление на няколко Icom
радиостанции — двупосочен аудио с ниско закъснение, серийни портове
(CAT), бриджнати към виртуални портове на клиента.

**Хардуер:**
- IC-7300 — свързано през USB (CI-V CAT + вграден USB аудио в едно)
- IC-746PRO — свързано през microHAM интерфейс (отделен CAT сериен
  порт, отделна USB звукова карта, PTT през RTS/DTR линия — не CAT)
- Поне 2 радиа, поне 2 едновременни потребители
- ACOM 1200S линеен усилвател, достъпен през ACOM eBox (Ethernet
  устройство с уеб-базиран интерфейс, не пряка RS-232 връзка към
  сървъра)

**Мрежа:** Клиенти и сървър в една локална мрежа (за сега). Минимално
изискване за latency. Без нужда от криптиране/автентикация отвъд
обикновен user login.

**Платформа:** Windows (клиент и сървър)

**Употреба:** Клубна и лична, с логване на сесии/предавания

**Ключови архитектурни решения:**
- CAT трябва да се вижда като стандартен COM порт за съществуващ
  софтуер (WSJT-X, N1MM+, fldigi)
- PTT метод конфигурируем per радио (различен за IC-7300 vs
  IC-746PRO+microHAM), с lock арбитраж (не queue)
- RC-28 поддръжка имплементирана директно в клиента (НЕ през RS-BA1),
  за да няма конфликт при няколко едновременни потребители
- CW модул поддържа множество варианти на ключове, не само един
- Admin панел за конфигурация на радиата — отдалечено достъпен, не
  само localhost на сървъра
- Приложенията са самостоятелни — самоинсталиращи се, без ръчна
  инсталация на Python/PostgreSQL от потребителя
- PostgreSQL за база данни (не SQLite)
- Сървърът се стартира ръчно, не като Windows Service
- Auto-update механизъм за клиент и сървър

**Технологичен стек:**
- Сървър: Python (asyncio), pyserial, RTP/UDP + Opus за аудио,
  PostgreSQL, FastAPI за admin панел
- Клиент: Python + PySide6 (Qt), com0com за виртуален COM порт,
  hidapi за RC-28
- Packaging: PyInstaller + Inno Setup/NSIS

## Фаза 1 — Основен prototype (1 радио, 1 потребител)

**Цел:** доказване на концепцията — CAT bridge + аудио bridge работят
end-to-end.

```
Разработи основен прототип на клиент-сървър система за отдалечено
управление на Icom IC-7300 в локална мрежа.

СЪРВЪР (Windows, Python/asyncio):
- Отваря CAT сериен порт на IC-7300 (CI-V) и rebroadcast-ва го през
  TCP към клиента (RFC2217 или custom protocol).
- Захваща аудио от USB аудио устройството на IC-7300, стриймва
  двупосочно през RTP/UDP + Opus codec.
- Основен PTT: CAT команда за IC-7300, single-user (без арбитраж
  за сега).
- PostgreSQL база данни: базова схема за бъдещи потребители/сесии/
  логове (само structure, без пълна имплементация все още).

КЛИЕНТ (Windows, Python + PySide6):
- Създава виртуален COM порт (com0com) локално, свързан през мрежата
  към сървъра — трябва да работи прозрачно с реален CAT софтуер
  (тествай с WSJT-X или подобен).
- Аудио клиент: приема/изпраща RTP/Opus поток.
- Минимален UI: статус на връзката, PTT бутон, аудио ниво индикатор.

ЗАДАЧА: работещ end-to-end пример — CAT команда от клиента стига до
радиото, аудио тече двупосочно с приемливо закъснение в LAN. Покажи
структура на проекта и инструкции за тестване.
```

## Фаза 2 — Второ радио, мулти-потребител, PTT арбитраж, стабилна device идентификация

```
Разшири системата от Фаза 1:

1. Добави второ радио: IC-746PRO през microHAM интерфейс (отделен
   CAT сериен порт, отделна USB звукова карта, PTT през RTS/DTR
   линия — не CAT команда). Абстрахирай PTT метода зад общ интерфейс,
   различен per радио.

2. Стабилна device идентификация (Windows): device registry при
   стартиране на сървъра, който сканира USB audio + serial устройства
   и ги идентифицира по VID/PID + USB сериен номер (ако има) + USB
   hardware path + WASAPI ContainerId — НЕ по device име или индекс,
   тъй като те се менят между рестарти/preplugване. Device watcher
   следи промени в реално време. При двусмислие — откажи стартиране
   на bridge-а и логни грешка.

3. Мулти-потребителска поддръжка: поне 2 едновременни клиента на
   различни радиа. Сървърът поддържа сесии, знае кой потребител е
   свързан към кое радио.

4. PTT арбитраж: lock (не queue) per радио — сървърът пази "кой
   предава в момента", отказва PTT заявка от втори потребител докато
   първият не приключи.

5. Session/transmission logging в PostgreSQL: потребител, радио,
   начало/край на връзка, начало/край на всяко предаване.

ЗАДАЧА: работещ пример с 2 радиа, 2 едновременни клиента на различни
радиа, демонстрация на PTT lock (опит за предаване от втори
потребител на заето радио бива отказан с ясно съобщение).
```

## Фаза 3 — Сървърен admin панел (отдалечен, ролеви достъп)

```
Добави администраторски уеб панел към сървъра от предишните фази.

- Уеб интерфейс (FastAPI + HTML/JS), достъпен отдалечено от всеки
  компютър в локалната мрежа (не само localhost).
- За всяко радио, конфигурируемо през панела:
  - Име и модел на радиото
  - CAT порт: избор от списък с открити сериен устройства (от device
    registry-то от Фаза 2), не ръчен текст
  - Baud rate, CI-V адрес
  - PTT метод: CAT команда / RTS линия / DTR линия — избираем per
    радио
  - Аудио вход/изход устройства: избор от списък (device registry)
  - Test/Verify бутон: активна проверка (напр. CAT "get frequency"
    заявка) преди прилагане на конфигурация, ясен успех/грешка UI
- Ролеви достъп: обикновени потребители виждат само клиентския
  интерфейс; администраторска роля (отделна автентикация) отключва
  admin панела.
- Конфигурацията се пази в PostgreSQL, поддържа презареждане на
  отделно радио без рестарт на целия сървър.
- Ако радио се преконфигурира докато е заето — блокирай промяната
  или изисквай потвърждение с ясно предупреждение към засегнатия
  потребител.

ЗАДАЧА: работещ admin панел, достъпен от друг компютър в мрежата,
демонстрация на промяна на CAT порт/PTT метод за радио "в движение"
без рестарт на сървъра.
```

## Фаза 4 — CW модул (всички варианти) + RC-28

```
Добави CW и RC-28 поддръжка.

CW МОДУЛ — унифициран "CW event stream" интерфейс към сървъра,
поддържащ множество превключваеми източници на клиента:
a) Локален iambic keyer (основен режим): paddle през USB-сериен
   адаптер, локален keyer генерира Morse timing, праща key-down/
   key-up събития с висок мрежов приоритет (отделна UDP опашка,
   различна от аудио/CAT трафика).
b) Прав ключ: on/off състояние директно по мрежата.
c) Текст → Morse: локален encoder от вписан текст.
d) External hardware keyer passthrough (WinKeyer-подобен): виртуален
   COM порт бридж или локална интерпретация на командите му.
Сървърът приема event stream-а и key-ва радиото през CAT или директна
key линия, според device profile-а на радиото (конфигурируемо от
admin панела от Фаза 3 — добави CW изходен метод там).

RC-28 ПОДДРЪЖКА:
- Клиентски driver за Icom RC-28 (USB VID:PID 0c26:001e, USB
  interrupt transfers, не стандартен HID клавиатура/мишка).
- Протоколът не е официално документиран — използвай USB capture
  (Wireshark + USBPcap) на реална комуникация RC-28↔RS-BA1 за
  потвърждение; референция: gi1mic/rc28_emulator на GitHub.
- Превежда физическите действия (главен диск, бутони) в CAT команди
  към текущо избраното радио в клиента.

ЗАДАЧА: демонстрация на CW keying от локален iambic keyer (paddle)
до реално key-ване на радиото, измерено закъснение. RC-28: поне
основна функция (главен диск → честотна промяна) работеща.
```

## Фаза 5 — ACOM 1200S / eBox интеграция

**Цел:** управление и мониторинг на линейния усилвател през мрежата,
без пряка RS-232 връзка до сървъра.

```
Добави поддръжка за ACOM 1200S линеен усилвател, достъпен през ACOM
eBox (отделно Ethernet устройство, което препраща команди по RS-232
към усилвателя и предлага уеб-базиран интерфейс).

КОНТЕКСТ:
- Сървърът комуникира с eBox по IP (конфигурируем адрес в admin
  панела от Фаза 3), не по локален сериен порт — eBox може да е
  навсякъде в локалната мрежа.
- Протоколът зад eBox уеб интерфейса НЕ е публично документиран от
  ACOM. Референтна информация за пълния RS-232 remote control
  протокол на самите ACOM 500S/600S/700S/1200S/2020S усилватели
  съществува в open-source проект (bjornekelund/ACOM-Controller на
  GitHub) — полезна отправна точка за структурата на командите, но
  eBox може да ги обвива по различен начин през HTTP.

ЗАДАЧА ЗА ПРОУЧВАНЕ (преди имплементация):
- HTTP request inspection (Chrome DevTools → Network tab) на реалната
  комуникация с eBox устройството, докато потребител го управлява
  през браузър — за установяване на точните endpoints, HTTP методи
  (GET/POST), и структура на данните (form fields, JSON, или друго).
- Ако eBox предлага чист programmatic API (JSON/REST) зад
  интерфейса — имплементирай HTTP client директно срещу него.
- Ако не — имплементирай HTTP client, който парсва HTML статус
  страницата (scraping) и изпраща form POST заявки, еквивалентни на
  действията в уеб интерфейса. Отбележи в кода, че този подход е
  чувствителен към firmware ъпдейти на eBox.

ФУНКЦИОНАЛНОСТ:
- Управление: standby/operate превключване, remote power on/off.
- Мониторинг: мощност, SWR, температура — периодично извличани и
  логвани в PostgreSQL; по избор изведени в клиентския UI.
- CAT mirror: ако eBox/усилвателят поддържа band tracking през CAT
  вход, сървърът препраща копие от CAT потока на активното радио
  (Icom CI-V формат) към усилвателя за автоматично band switching.
- Admin панел (Фаза 3): нова секция за IP адрес на eBox, credentials
  ако се изискват, и дали усилвателят е споделен между радиата или
  dedicated към едно от тях.
- [По избор] Safety lockout: блокирай PTT ако усилвателят докладва
  fault състояние (overtemp, висок SWR).

ЗАДАЧА: работещ пример — сървърът чете статус от eBox (мощност/SWR/
температура) и може да превключи standby/operate дистанционно.
```

## Фаза 7 — Пакетиране, инсталация, auto-update

```
Пакетирай сървър и клиент за самостоятелна дистрибуция.

- PyInstaller (или еквивалент) за standalone executable на двете
  приложения.
- Inno Setup или NSIS инсталатор:
  - Клиент: silent инсталация на com0com драйвер (изисква admin
    права), USB backend драйвери при нужда.
  - Сървър: bundled/автоматизирана инсталация на PostgreSQL.
  - Desktop/start menu shortcuts; БЕЗ auto-start при boot (ръчно
    стартиране за сървъра).
- Auto-update механизъм: периодична проверка за нова версия (version-
  check endpoint или GitHub releases), автоматично сваляне и
  прилагане на обновление без ръчна преинсталация от потребителя.
- Чиста деинсталация: премахва всички компоненти включително
  драйверите; при деинсталация на сървъра — питай дали да се запази
  PostgreSQL базата с логовете.

ЗАДАЧА: готов .exe инсталатор за клиент и сървър, тестван на чиста
Windows машина без предварително инсталиран Python.
```
